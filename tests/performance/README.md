# Isolated 20-user performance harness

These tools use only newly created OS temporary directories with a `fixture.json` marker. They do not open the production database. Seed creation initializes `buildApp`'s real migrations, closes it, then inserts fictional fixture data transactionally. Baseline immutability triggers are temporarily removed only in the fresh fixture and restored before use. Real HTTP measurements run Fastify/SQLite in a separate child process with `NODE_ENV=production`; only this loopback fixture disables Secure cookies. Production business authorization and CSRF remain enabled. A production `client/dist` is required, and served by a test-owned static handler.

Run from `project/`, using Node 24.13.1:

```sh
fnm exec --using=24.13.1 npx vitest run tests/integration/performance-seed.test.ts
fnm exec --using=24.13.1 npm run build
fnm exec --using=24.13.1 npx tsx tests/performance/run.ts --tasks 2000 --users 20 --quick --out /tmp/gw-performance/smoke
fnm exec --using=24.13.1 npx tsx tests/performance/run.ts --tasks 2000 --users 20 --duration-seconds 300 --warmup-seconds 60 --out /tmp/gw-performance/2000-20
fnm exec --using=24.13.1 npx tsx tests/performance/suite.ts --profile full --out /tmp/gw-performance/full
```

`--tasks`: 1000, 2000, 5000 **execution** tasks; summary parents are additional. `--users`: 1, 5, 10, 20 independent accounts. `--dense`: ~3 instead of 1 predecessors per nonroot task (the exact count is recorded; DAG roots are unavoidable). `--dist PATH` and `--source-root PATH` compare a preserved production build and an unchanged source tree. `--quick` defaults to 8-second mixed phase, 1-second warmup and 100–300 ms think time, and labels a functionally successful result **SMOKE_ONLY**. It cannot establish capacity. Standard think time is seeded 3–8 seconds; test time controls the mixed phase only. Setup, coverage probes, concurrency bursts and consistency verification are additional.

The full suite runs sequentially: 1000/2000 tasks × 10/20 users for 5 minutes each; the 2000/20 case totals 3 repetitions; a 30-minute 2000/20 soak; a 5000/20 boundary run; a 2000/20 dense case, and five disjoint projects with 400 execution tasks each. `--profile matrix` runs only the 4 normal cases. `--profile smoke` checks 1/5/10/20 users. `--resume` is disabled; each suite run measures fresh source/build state. Do not overlap benchmark runs or run a build/test suite while measuring.

The fixture has 20 fictional member-linked accounts (1 manager, 2 project administrators, 17 members), 20 groups, 20% execution tasks under summary parents, 10% unscheduled, date-valid DAG edges, comments on every execution task, independent accepted review submissions, 20 risks, 3 immutable baselines, and 90 daily snapshots. History preserves no completed outcome before its actual completion date. All names, evidence and data are marked DEMO. Root nodes reduce the average number of incoming edges; dense edges are deduplicated and date-checked. Every seed verifies counts, foreign keys, SQLite integrity, task parentage, working days, DAG ordering, dependency dates and review evidence.

User actions follow four reads then one write, alternating comments and independent start/progress updates; read variants include overview, task list/detail, Gantt, analytics, risks, groups, settings, notifications and revision. The optimized task query/detail API is detected during setup; legacy sources use full `/tasks`. Version refresh requests and retry attempts are additional real requests and reported separately. Coverage includes 100-task schedule preview, 20 simultaneous list requests, independent-task concurrent comment and progress writes, and 20 stale same-task progress transitions from the manager session. Transition probing accepts exactly one write; a separate 20-comment append probe accepts all 20 when the structure-version contract is available (legacy global-version servers accept one); other version conflicts are reported independently. Each confirmed comment is verified exactly once in the persisted DB after server shutdown.

`report.json` contains environment/source/build metadata, raw requests, p50/p95/p99 by operation and phase, response bytes/status/error codes, retry and final write-success counts, integrity checks and CPU/RSS/event-loop/job samples. `requests.ndjson` is the raw HTTP trace and `report.md` the readable summary. Server metrics use IPC and a test-only readonly SQLite connection once per second. Its overhead remains part of measured load. `busyResponses` counts surfaced HTTP 503 responses; internal SQLite waiting time is not directly instrumented. Production job timers and write hooks remain enabled; the clock advances from a fixed fixture epoch. A normal 5-minute run may not cross a 15-minute risk schedule; the 30-minute soak does.

Full runs use 60-second warmup and independent 30-second revision polling per active user, in addition to the 80/20 action mix. Coverage includes a 366-day inclusive analytics window. Successful reads validate project and task identity, pagination totals, and seeded analytical counts. Full runs assert per-operation and aggregate ordinary p95 ≤ 1 s, bulk-preview p95 ≤ 2 s with success, query p99 ≤ 2 s, unexpected error rate < 0.1%, independent writes finally successful ≥ 99%, exactly one stale transition winner with progress=60 and one version increment,19 version409 responses and no rejected audit markers, no lost/duplicate acknowledged writes, task-count/FK/integrity preservation. Expected 409 revision conflicts are counted separately from unexpected errors. Failing full gates exit 1 after saving reports. Performance gates are descriptive in quick mode, but response contracts, freshness, write/conflict correctness, and data-integrity failures still exit 1. No browser rendering time is inferred from these HTTP metrics; browser QA must be run separately.

Programmatic interfaces: `createFixture({tasks,dense?})` returns `{directory,dbPath,projectId,accounts,counts,cleanup}`; `validateFixture(db,projectId,count)` checks seed invariants; `startServer({dbPath,sourceRoot?,dist?})` returns `{address,pid,samples,logs,stop}`. Call `stop()` before fixture `cleanup()`.

Seed v2 marks historical comment audit events as already seen by notifications, preventing artificial first-write history replay. Re-run v1 baseline reports before comparing against v2.

The soak gate requires at least 1,200 telemetry samples, compares median RSS from the first and last mixed-phase quarters (growth limited to max(64 MiB,20% of initial median)), requires zero failed jobs, final pending/running backlog at most initial+25, final oldest due-job age ≤120 seconds, last-quarter median oldest due-job age ≤60 seconds, and at least two successful periodic risk evaluations. These explicit budgets are diagnostic acceptance limits, not a claim of zero allocation growth.

Five-project isolation: `npx tsx tests/performance/isolation.ts --quick --out /tmp/gw-performance/isolation-smoke`. Twenty accounts have disjoint four-person memberships; all 20 cross-project reads and writes must be denied, authorized writes must leave other projects unchanged, response identifiers must remain in scope, and acknowledged comments must persist exactly once. The full suite includes its five-minute workload with 60-second warmup.

After the mixed phase, a confirmed comment starts a five-second freshness probe. A test-owned read-only database connection verifies the latest daily snapshot plan version catches up to the current plan and risk evaluation time reaches the comment update time. Target and observed values plus elapsed time are retained; this functional gate applies even in quick mode. Use `--warmup-seconds 60` to test steady-state correctness after draining startup jobs.

Browser measurements: `fnm exec --using=24.13.1 npx tsx tests/performance/browser.ts --iterations 5 --out /tmp/gw-performance/browser`. Build the production client first and run without another benchmark or test suite. The harness uses real login, an isolated 2000-task SQLite fixture, and Chrome at 1440/390/320 px. It measures first render, task filters/search/pagination/detail, Gantt expansion and five-second continuous scrolling, keyboard End/Home, and complete analytics tabs including a 366-day window. It retains raw frame intervals/long tasks, response statuses, screenshots and Playwright traces. First render/expand p95 must be ≤3s, task and analytics filtering/tab changes/pagination ≤1s, continuous-scroll frame p95 ≤33ms and longest scroll long task ≤200ms; task/Gantt DOM bounds and viewport overflow are also asserted. `--quick` runs one iteration and reports timing descriptively.

Write mix revision: mixed writes now alternate comments and start/progress updates (40/41) on each member's independent task. A separate 20-user concurrent transition probe checks the same update path. Transition timings and final success are separate, audit markers must occur exactly once, and final task state is verified. Earlier baseline-v2 comment-only mixed reports remain useful read-path evidence but do not represent an identical write workload.

The post-mixed bulk probe first submits 100 priority updates with one stale final item and verifies a version conflict leaves every targeted row unchanged. It then applies a valid 100-task priority batch, asserts affectedCount=100, each version increments once, all priorities persist and each audit marker occurs exactly once. Bulk-write p95 has its own 2-second gate and is excluded from ordinary-write 1-second limits. Earlier baseline reports did not include this probe.

Browser observer comparison: default runs retain Playwright tracing with screenshots/snapshots. `--no-trace` disables that recorder while retaining raw animation-frame intervals, Long Tasks API entries, HTTP timings and scenario screenshots. Compare the same source/build in an otherwise idle environment and retain both reports; a difference is observer overhead, not evidence of application-code speedup.

HTTP runners print one lightweight progress JSON line every30 seconds: phase, elapsed seconds, completed HTTP count, acknowledged task writes/attempts, latest RSS and pending/running job count. The load-generator timer is cleared before server shutdown and does not issue extra requests.

CPU diagnosis: add `--cpu-profile-dir /tmp/gw-performance/cpu/profiles` to `run.ts` to enable Node's sampling profiler only in the server child. The report marks this as diagnostic, including observer overhead; do not use profiled timings as capacity evidence. After orderly shutdown, summarize the resulting `.cpuprofile` with `npx tsx tests/performance/profile-summary.ts PROFILE.cpuprofile OUT.json`. Sampled inclusive stacks overlap, exclusive categories do not; startup and warmup are included. Native SQLite waits can be attributed to a JS caller, so sampled stack time is not exact pure CPU or per-job latency.

Clone diagnosis: `npx tsx tests/performance/clone-diagnostic.ts /tmp/gw-performance/clone` measures ten iterations each of structured cloning, a JSON round trip, and parsing a pre-serialized JSON string for actual 2000-task plan and full analytics DTOs. It checks JSON/value equality outside each timer and reports special-value or repeated-reference paths. Parse-only timing excludes serialization; equal JSON values do not establish identical object-reference semantics.

Tail-latency diagnosis is opt-in: add `--diagnostic` to `run.ts`. It records client request milestones and correlation IDs, server `onRequest`/`onResponse` callback intervals, GC entries, raw `process.resourceUsage()`/memory samples, and the existing telemetry collection duration. Reports say `DIAGNOSTIC` and preserve `evaluatedVerdict`; these timings cannot replace capacity evidence. The callback interval is not pure handler time: `onResponse` may run after the client receives the response. Node resource counters vary by platform; zero I/O counters do not establish absent I/O.

Observation streams allow 32 MiB per file, 256 KiB pending writes, and 16 KiB per record. They drop records instead of delaying requests when budgets are reached. Inspect terminal `diagnostic_summary`, `diagnostic-lifecycle.json`, and `server-diagnostic-lifecycle.json` for dropped records, cleanup errors, and `observationComplete`; incomplete observation cannot support a claim that no GC/resource event occurred. Stop is idempotent with a five-second flush timeout. This switch is off by default and adds no production route. Optional host `vm_stat`/`iostat` and power logs must be labeled as whole-host observations, with their initial cumulative rows excluded from interval comparisons.

Validate the observer's bounded slow-write and disk-error paths with the repository test runner:

```sh
fnm exec --using=24.13.1 npx vitest run tests/performance/diagnostics.test.ts
```

Browser scroll driver v2: the continuous-scroll action reads its fixed maximum distance once before the animation loop, writes only `scrollTop` on each frame, and verifies the final range/position within 1px plus the last logical row. The full distance, five-second duration, 2000 tasks, three viewports, five iterations, frame/LongTask observers and thresholds are unchanged. The v16 CDP diagnostic located synchronous Layout under the former driver's per-frame `scrollHeight` read. Reports identify `metadata.scrollDriver.version=2`; this corrects measurement overhead, not product code. Retain v15's valid FAIL and do not attribute all earlier slow frames to the driver or claim product speedup from a cross-driver comparison.
